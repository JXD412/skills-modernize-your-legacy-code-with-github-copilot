# COBOL Account Management Test Plan

## Purpose and scope

Validate the current single-account behavior with business stakeholders before migrating to Node.js. The source of truth is [main.cob](../src/cobol/main.cob), [operations.cob](../src/cobol/operations.cob), and [data.cob](../src/cobol/data.cob). See the [application documentation](README.md) for the architecture and build/run instructions.

The application supports viewing, crediting, and debiting one in-memory balance. It does not implement student accounts, customer identification, payment categories, transaction history, or persistent storage. These are not assumed requirements.

## Execution and review conventions

- Build and run the COBOL application using the instructions in the [application documentation](README.md#running-the-program). Record compiler/runtime details alongside execution evidence, especially for characterization cases.
- Start a fresh process for each case unless its preconditions explicitly require a running session. A fresh process starts with a balance of **1000.00**. Perform setup transactions through the menu unless a case specifies a direct subprogram harness.
- Enter each menu choice and amount separately. After a successful or rejected transaction, select **1** to verify the stored balance, not just the transaction message. End interactive cases with **4**.
- Amounts below are logical monetary values. COBOL uses unsigned `PIC 9(6)V99` fields with two implied decimal places; capture the literal output in Actual Result rather than assuming it includes a decimal separator or currency symbol.
- `BUS` cases cover business behavior, `UI` cases cover menu integration, `INT` cases cover internal contracts, and `CHAR` cases document validation gaps or numeric limitations requiring stakeholder decisions.
- Actual Result is initially **Not run**. Status is **-** until execution, then **Pass** or **Fail** against the documented expectation. Stakeholder approval is a separate decision to record in Comments; a passing legacy behavior is not automatically an approved future requirement.
- Characterization cases deliberately do not invent validation, rounding, or overflow rules absent from the source. Record the observed outcome and obtain an approved expectation before turning those observations into Node.js acceptance tests. Run each potentially invalid input in an isolated process; if it fails or cannot exit normally, record that outcome and end that test process.

## Using this plan for the Node.js migration

- Review every business expectation and decision comment with stakeholders. Record the approved behavior, approver, date, and any intentional departure from COBOL in Comments.
- Map `BUS` cases to service-level unit tests and selected end-to-end integration tests. Use exact monetary assertions, such as integer minor units, rather than approximate binary floating-point comparisons.
- Map `UI` cases to the replacement interface's integration tests. If the interface changes from a console to an API or web UI, preserve approved business outcomes without requiring COBOL-specific prompts or numeric display formatting.
- Map `INT` cases to the new storage/service contracts where those contracts remain relevant. The direct-call harness is a future testing aid, not an existing test tool. Do not copy silent unknown-operation behavior without an explicit decision.
- Resolve `CHAR` cases before implementing their Node.js acceptance tests. Legacy runtime observations are evidence, not automatically desired requirements.
- Use fresh state for independent tests; retain state only within explicitly sequential cases. Reset-between-processes behavior must be revisited if persistent storage is approved.
